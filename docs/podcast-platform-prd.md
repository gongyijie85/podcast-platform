## 1. 产品目标（Product Goals）

平台聚焦"图书 → 播客"的一键式自动化生产，核心目标如下（三者正交、可独立衡量）：

1. **降低制作门槛**：让无音频/剪辑经验的内容运营者，仅通过 ISBN 即可在 10 分钟内产出一期可发布级别的播客音频。
2. **保障产出质量**：通过固定双人对话脚本框架 + 情绪标注 + 独立音色 + 分段 BGM，保证产出的播客在"结构完整度、口语化、可听性"上达到 90 分位（相对人工主播）。
3. **支撑规模化复用**：单次支持 1~20 本书批量处理；登录用户项目可云端持久化、参数可复用（常用音色、BGM 偏好），复刻一期类似播客的耗时 < 3 分钟。

---

## 2. 用户故事（User Stories）

1. **作为内容运营者**，我希望批量粘贴多个 ISBN 并自动拉取书名、作者、封面、简介，这样就不用逐本手动录入，节省前期准备时间。
2. **作为播客制作人**，我希望 AI 按"开场 → 介绍 → 解读 → 评价 → 建议 → 收尾"的标准框架自动生成双人对话脚本，且每段带情绪标注，这样后期人工微调的工作量最小。
3. **作为品牌调性负责人**，我希望为主持人和嘉宾分别挑选不同音色并在线试听，这样可以让节目拥有稳定的人设辨识度。
4. **作为追求氛围感的听众创作者**，我希望开场、正片、片尾用不同 BGM，并对音量做独立渐入渐出调节，这样节目在情绪过渡上更专业。
5. **作为后期剪辑**，我希望脚本编辑器和音频播放器联动——改完脚本可一键重合成，字幕能精准对齐音频并支持波形预览定位——这样返工成本极低。
6. **作为登录用户**，我希望项目草稿、历史播客、常用偏好能云端保存，下次打开继续编辑，这样多设备/跨时间工作流不会断。

## 3. 需求池（Requirements Pool）

> 优先级：P0 = 必须有（上线阻塞）/ P1 = 应该有（首版增值）/ P2 = 锦上添花
> 验收标准以"可测"为原则，给出最小判定条件。

### P0 核心链路

| ID | 需求 | 验收标准 |
|----|------|----------|
| P0-01 | **ISBN 批量导入**——支持手动输入（每行/逗号/空格分隔）与文本粘贴两种方式，提交后系统对每个 ISBN 做格式校验 | 输入 13 位数字或 10 位数字组合；非法格式（位数错、含字母）被标记为红色行，鼠标悬停显示原因；至少支持一次提交 1~20 个 ISBN |
| P0-02 | **图书元数据抓取**——对接图书 API（Open Library / 豆瓣 ISBN 公开接口），拉取书名、作者、封面、简介 | 单本 < 3s 返回；抓取失败的 ISBN 在列表中标"⚠️ 抓取失败"并允许重试；封面图支持 200x200 缩略图展示 |
| P0-03 | **AI 播客脚本生成**——按六段式框架（开场→介绍→解读→评价→建议→收尾）生成双人对话；每条台词带情绪标签（如 `[开心]`、`[沉思]`、`[激昂]`） | 调豆包大模型；返回 JSON 包含 `segments[]`，每段含 `speaker`(host/guest)、`text`、`emotion`；脚本总字数 1500~3000 字；生成耗时 < 30s |
| P0-04 | **脚本在线编辑**——富文本编辑器，支持格式化、撤销/重做（Ctrl+Z / Ctrl+Y）、查找替换 | 修改后按钮"重新合成音频"置为可点击；本地草稿自动每 5s 保存一次（游客 localStorage，登录用户同步云端） |
| P0-05 | **TTS 语音合成**——内置 ≥ 4 种音色，可为主持人/嘉宾分别指定；提供试听按钮 | 试听时长 ≥ 10s；合成整期音频 < 90s（1500 字脚本为基准）；合成失败时该段标红并支持单独重试 |
| P0-06 | **BGM 曲库**——内置分类（轻松/科技/人文/纪实等），每类 ≥ 3 首 | 用户可为开场/正片/片尾三段分别选曲；同曲不可重复选入相邻段落时给出提示 |
| P0-07 | **BGM 音量与渐变**——支持人声与 BGM 独立音量条（0~100）；支持 0.5s/1s/2s 渐入、渐出 | 试听时人声不被 BGM 盖过；峰值音量在 -3dB 以内避免爆音 |
| P0-08 | **音频合成与导出**——支持两种模式：①逐本 ISBN 独立成期 ②多本合并为单期；导出 MP3 + SRT/VTT 字幕 + TXT 脚本 + PDF 脚本 | MP3 采样率 44.1kHz、码率 192kbps；字幕时间轴与音频对齐误差 < 200ms；多文件可打包 zip 下载；单文件 > 50MB 时提示 |
| P0-09 | **字幕生成**——自动按 TTS 时间戳生成 SRT 和 VTT 两种格式，文件随音频一起导出 | SRT 序号连续；VTT 含 `WEBVTT` 头；任一格式错误时下载按钮置灰 |
| P0-10 | **四步流程导航**——选书 → 配置 → 生成 → 预览&导出，全流程响应式（PC/平板/手机） | 每步有清晰标题、步骤指示器（1/4、2/4 …）；未完成上一步时禁用"下一步"按钮 |
| P0-11 | **生成进度可视化**——实时显示百分比 + 当前阶段（拉取/脚本/TTS/字幕），可中途取消 | 进度条不卡死；取消时已生成资源不删除，作为草稿保留 |
| P0-12 | **异步任务队列**——后端用消息队列处理 AI 脚本、TTS、字幕，避免 HTTP 超时 | 客户端轮询或 WebSocket 推送进度；同一用户任务排队不阻塞 |
| P0-13 | **异常处理**——ISBN 非法、API 超时、生成超时、网络中断均有友好弹窗 + 自动重试（最多 3 次） | 用户可手动点"重试"；重试失败写入错误日志 |
| P0-14 | **游客/登录双模式**——游客可完整体验但刷新数据丢失；登录用户云端持久化项目、偏好 | 登录入口在右上角；登录后草稿自动从云端拉取合并 |

### P1 体验增强

| ID | 需求 | 验收标准 |
|----|------|----------|
| P1-01 | **音频波形可视化**——播放器下方展示音频波形，跟随播放进度高亮当前位置 | 波形渲染 < 2s；点击波形可跳转播放位置（误差 < 1s） |
| P1-02 | **字幕叠加播放**——播放器内同步显示当前台词字幕 | 高亮当前行；点击字幕行跳转音频；字号、行间距可调 |
| P1-03 | **历史播客记录**——登录用户可查看过去生成的所有播客，支持二次编辑/重新下载 | 列表按时间倒序；每条记录含封面、时长、生成时间 |
| P1-04 | **常用偏好记忆**——登录用户最近使用过的音色/BGM 在选择器顶部置顶 | 偏好项最多保留 5 个 |
| P1-05 | **加载与结果反馈**——所有按钮操作有 loading 状态；成功/失败用 MUI Snackbar 提示 | 成功/失败配色区分（绿/红）；3s 自动消失 |

### P2 锦上添花

| ID | 需求 | 验收标准 |
|----|------|----------|
| P2-01 | **多语言界面**——中/英双语切换，i18n 配置 | 切换不刷新页面 |
| P2-02 | **脚本模板**——除默认框架外，预置"深度书评"、"轻松对谈"、"学术解读"等模板供用户选择 | 切换模板后脚本结构随之调整 |
| P2-03 | **播客封面生成**——根据书籍封面自动生成播客封面（可手动调整） | 输出 3000x3000 PNG |
| P2-04 | **分享链接**——生成完成后可生成可分享的试听链接（仅含音频+字幕，不可编辑） | 链接 7 天有效期 |
| P2-05 | **音效素材**——除 BGM 外，允许插入环境音（咖啡馆、雨声等）作为段落背景 | 同 BGM 的音量控制 |

## 5. 待确认问题（Open Questions）

> 以下问题在进入开发前需与主理人/架构师对齐，否则可能影响工时评估。

1. **后端语言选型**：需求中提到 Node.js / SpringBoot 二选一。团队是否已有技术栈偏好？若没有，建议 Node.js（NestJS）以加快 MVP 进度。
2. **第三方 API 选型**：
   - 图书元数据 API：Open Library（免费/英文好）vs 豆瓣 ISBN（中文好但需授权/不稳定）vs Google Books？建议主备双通道。
   - TTS 服务：豆包、火山引擎、微软 Azure、AWS Polly 哪一个作为默认？价格/音色版权需确认。
   - 大模型：脚本生成是只用豆包一家，还是支持多模型切换？
3. **登录方式**：邮箱密码？手机号？第三方（微信/GitHub）？是否需要企业 SSO？
4. **文件存储**：本地磁盘 vs 对象存储（OSS/S3）？用户音频文件是否需要长期保留（涉及成本）？是否需要 CDN 加速下载？
5. **生成超时阈值**：单期播客合成总时长上限多少？超过是否强制拆分或失败？（建议单期 < 15 分钟）
6. **数据保留策略**：游客数据丢失可接受；登录用户的历史播客保留多久（永久/1 年/用户主动删除）？涉及 GDPR 合规吗？
7. **多本书合并模式的合并逻辑**：是按 ISBN 顺序串讲？还是 AI 总结跨书主题？需主理人确认。
8. **PDF 脚本格式**：仅纯文本 + 标题样式，还是含剧本舞台说明（人物、情绪、背景音）？
9. **并发与限额**：单用户同时能跑多少个生成任务？是否需要付费配额控制？
10. **国际化范围**：P2-01 多语言界面 v1 是否要做？若做，最低支持哪些语言？

## 6. 关键决策摘要（给架构师的一页纸）

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 前端框架 | Vite + React + TypeScript + MUI + Tailwind | 团队默认栈，组件库丰富，音频波形/富文本生态成熟 |
| 后端框架 | 建议 Node.js (NestJS) + BullMQ | 与前端同语言；BullMQ 自带任务队列，契合异步生成 |
| 存储 | 对象存储 (OSS/S3) | 音频/字幕文件大，OSS 成本低 |
| 数据库 | PostgreSQL（用户、项目、偏好）+ Redis（任务队列、缓存） | 关系型 + KV 经典组合 |
| 第三方 API 抽象 | 全部走"适配器模式"，可替换 | 避免被单一供应商绑定 |
| 脚本生成提示词 | 六段式框架 + 情绪标签，写入 system prompt 模板 | 稳定可复现 |
| 进度推送 | WebSocket 优先，回退 SSE，最后轮询 | 体验与兼容性兼顾 |
| 移动端 | 响应式自适应（不做独立 App） | 节省工时，符合需求 |
